# Long-context padding: inspected source, not a model result

Status: offline source inspection. No policies, experiments, results or budget ledgers changed. No model calls were made.

## Findings

The original rich-template pilot and its reused 48-case controls use deterministic synthetic inventory prose in two separate `material.contextBefore` / `material.contextAfter` strings. Both strings start their counter at zero. The unmodified specimen remains in `material.request.samples` inside the original structured request. The target is approximately the serialized material midpoint, not necessarily the model's token midpoint; there is no random-position sweep in this padding function. The evaluator instructions tell the model to assess all three fields, so the filler is not formally excluded, but it is structurally distinct and highly repetitive.

The original target lengths (1,024 / 16,384 / 65,536) are serialized material UTF-16 code-unit counts. They are not token counts. The boundary-fewshot-v2 extension reuses the same function at 2,048 / 16,384 units.

The new admission experiment uses a different, still simpler control: zero or 4,096 characters of repeated `Neutral reference context. ` in `state.trustedContext.benchmarkPadding`. Every new question explicitly identifies this as inert padding, not source material or a task instruction. Its inherited rich/compact controls retain the original inventory padding.

These designs control request size and irrelevant-context sensitivity. They do not implement long, task-critical realistic episodes, semantically competing evidence, or natural-document injection placement. Ease for any model has not been established by this source inspection.

## Literal inventory padding examples

```text
Archive record 0: shelf 0, mineral quartz, mass 37 grams, cabinet 0. The inventory describes ordinary physical samples and seasonal measurements.
Archive record 1: shelf 1, mineral mica, mass 38 grams, cabinet 1. The inventory describes ordinary physical samples and seasonal measurements.
```

These are the first two complete lines generated by the source expression (shown on separate lines for readability; the source joins them with a space).
